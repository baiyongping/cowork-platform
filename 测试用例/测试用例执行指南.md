## 二、测试执行流程

### 2.1 单模块测试流程

#### 步骤1：阅读测试用例
1. 打开对应模块的测试用例文档
2. 理解功能概述和测试目标
3. 检查测试前提是否满足

#### 步骤2：执行测试用例
```
按照测试用例编号顺序执行：
TC-XXX-001 → TC-XXX-002 → TC-XXX-003 ...
```

#### 步骤3：记录测试结果
对每个测试用例记录：
- [ ] ✅ 通过 - 实际结果符合预期
- [ ] ❌ 失败 - 实际结果不符合预期（记录详细信息）
- [ ] ⚠️ 阻塞 - 无法执行（记录原因）

#### 步骤4：处理测试失败
```
发现问题 → 记录详细信息 → 创建Bug报告 → 通知开发修复
```

### 2.2 测试记录模板


## 三、回归测试执行

### 3.1 什么时候执行回归测试？

**触发条件**：
1. ✅ 修改了已完成功能的核心文件
2. ✅ 修改了共享组件或工具函数
3. ✅ 修改了全局状态管理
4. ✅ 修改了数据库结构
5. ✅ 修改了API接口

### 3.2 回归测试执行步骤

#### 步骤1：识别影响范围
```
分析本次修改 → 列出可能受影响的功能模块
```

#### 步骤2：执行快速回归测试
对每个受影响的模块，执行其**回归测试检查清单**：

**示例：员工管理模块回归测试**
```markdown
## 回归测试检查清单

- [ ] 员工列表正常加载显示

- [ ] 部门关联功能正常
- [ ] 权限控制正确
- [ ] 操作日志正常记录
```

#### 步骤3：记录回归测试结果
```markdown
## 回归测试报告

**修改内容**: 优化了员工列表加载逻辑

```

## 六、测试技巧

### 6.1 使用浏览器开发者工具

**Console标签**：
- 查看JavaScript错误
- 查看调试日志
- 验证数据格式

**Network标签**：
- 查看API请求和响应
- 验证请求参数
- 检查响应时间

**Application标签**：
- 查看localStorage
- 验证Token保存
- 检查Cookie

### 6.2 测试数据管理

**创建测试数据**：
```
使用系统功能创建测试数据，而不是直接修改数据库
```

**清理测试数据**：
```
测试完成后，删除测试创建的数据，保持环境干净
```

**备份测试数据**：
```
对重要的测试场景，备份测试数据，方便重复测试
```

### 6.3 边界值测试

**总是测试以下边界条件**：
- 空值、null、undefined
- 最小值、最大值
- 特殊字符、表情符号
- 超长文本
- 并发操作

### 6.4 异常场景测试

**不要只测试正常流程**：
- 网络断开
- 权限不足
- 数据库连接失败
- 并发冲突
- 重复提交

## 八、常见问题FAQ

### Q1: 测试用例执行顺序重要吗？
**A1**: 是的。建议按用例编号顺序执行，因为有些用例可能依赖前面的测试数据。

### Q2: 发现Bug后应该继续测试吗？
**A2**: 
- 如果是阻塞性Bug（影响后续测试），停止测试，等待修复
- 如果是一般Bug，记录后继续测试其他用例

### Q3: 回归测试需要执行完整测试用例吗？
**A3**: 不需要。回归测试执行**回归测试检查清单**即可，这是精简后的核心测试点。

### Q4: 测试用例和实际功能不一致怎么办？
**A4**: 
- 如果是功能变更，更新测试用例
- 如果是测试用例错误，修正测试用例
- 记录测试用例的修改历史

### Q5: 如何判断测试是否完成？
**A5**: 
- ✅ 所有测试用例执行完毕
- ✅ 所有阻塞性Bug已修复并验证
- ✅ 回归测试全部通过
- ✅ 测试报告已生成
